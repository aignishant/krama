# 2.2 — Defining `n`

## 1. The one-line answer

Nobody hands you the `n` in a cost claim — you choose what to measure the input by, and choosing
the wrong thing is how confident people end up with an answer that is not merely imprecise but
the wrong shape entirely.

---

## 2. The story

The licence is painted on the hull in white letters a hand high, and it has said the same thing
since before Bhola took the ferry over from his father: **22 PASSENGERS**.

The crossing is four hundred metres of brown water and it runs from before first light until the
last bus. Bhola counts heads as they step down off the bank, out loud, in the way a man counts
who has counted the same thing eighty times a day for thirty years. At twenty-two he puts his arm
across and the twenty-third waits for the next crossing, and nobody argues, because everybody
here has known somebody who drowned upriver at Sonarpur when a boat went over in the monsoon.

On an ordinary morning the count is a good rule. Twenty-two people going to work, with a bag
each, and the boat sits where it should sit and the water stays a comfortable distance below the
rail.

Thursday is market day, and on Thursday the same twenty-two people come back across in the
afternoon with what they have bought. Sacks of rice. A tin trunk. Once, memorably, a goat. The
count is still twenty-two. The boat is not the same boat. Bhola has known this for thirty years
in the way you know something with your knees rather than your head, and what he does about it is
unwritten: on Thursdays he stops at eighteen, or at fifteen if he sees cement, and if a man
wheels on a bicycle with four bags of cement on the carrier, that man is not one passenger, he is
the afternoon's argument.

His father would have said the licence is wrong, and it is. But it is also the only thing on the
boat that can be checked from the bank by a man who is not on it. There is no weighbridge at a
river crossing. There is no way to know what a sack holds without opening it. There is a number
you can count without touching anything, and there is the number that actually decides whether
the boat comes back, and the whole of Bhola's competence is knowing when the first has stopped
standing in for the second.

---

## 3. The idea in plain language

The count of heads is the **input size** — and Thursday is what happens when it stops
representing the thing that actually drives the cost.

Say you have a procedure and you want to state what it costs. Cost as a function of *what*? Of
the input, obviously — but the input is a whole object, and a function needs a number. So you
pick a number that summarises the input, and you call it `n`. That pick is a decision, it is
yours, and everything downstream of it inherits whatever you got wrong.

The honest default, the one theory uses when it wants to be unambiguous, is the **number of bits
it takes to write the input down**. That measure is never wrong, because it counts what is
actually there. It is also awkward for everyday work, so almost everyone uses a proxy instead:
the number of *elements*. "A list of `n` integers."

That proxy is legitimate under exactly one condition, and it is 2.1's third assumption: each
element must fit in one cell — one machine word. When it holds, elements and bits are within a
constant factor of one another, and `Θ` cannot tell them apart. When it does not hold, the proxy
is Thursday, and the answer you get is not slightly off. It is a different shape.

Four places the proxy stops standing in for the thing:

**The input is one number.** Give a procedure a single integer `m`. There is one element, so `n`
is 1 and every procedure is `Θ(1)`, which is absurd. The size of a single integer is the number
of digits — about `log m` bits — and a procedure that loops `m` times is exponential in that. All
of cryptography sits on this distinction. It is also the caveat Day 162 is named after, when a
table of size `W` shows up in a dynamic programme and looks polynomial (`DPA-05`).

**The input is a graph.** There are two numbers, the vertices and the edges, and they are
genuinely independent — a graph on a thousand vertices has anywhere between zero and half a
million edges. "`O(n)`" for a graph procedure is not imprecise, it is unanswerable. This is why
you will see `O(V + E)` written out and never abbreviated (`GRA-03`, Day 129).

**The input is text.** 1.1 ended on this: `"café"` is four code points, or five if the accent is
written separately, or five bytes in UTF-8, or four things a reader would call letters. Four
different `n`s for one string, differing by more than a constant when the script is Devanagari or
an emoji sequence. `STR-01`, Day 21.

**The input is a grid.** A thousand-by-thousand image: is `n` a thousand or a million? Both
conventions are in use, `O(n²)` and `O(n)` name the same procedure under them, and the two people
in the interview are each certain the other is wrong.

> **Formally:** the size `|x|` of an input `x` is the number of bits in a reasonable encoding of
> it. A cost claim is a function of `|x|`, or of explicitly named parameters (`V` and `E`; rows
> and columns; elements `n` and word width `w`). A claim that names no parameter has not been
> made.

## 4. Where this actually shows up

- **TLS and RSA key sizes.** A certificate is described as 2048-bit, never by the value of its
  modulus — and the value is a number with over six hundred digits. The security argument is
  precisely a statement about input size: the best known factoring procedures run in time that
  grows exponentially in the *number of bits*, while everything you do with the key (multiply,
  exponentiate) grows polynomially in the same measure. Get the measure wrong and the entire
  argument inverts, because `√m` steps against a six-hundred-digit `m` sounds small and is not a
  number of operations the universe can supply.

- **BigQuery and Snowflake billing.** Both charge by **bytes scanned**, not by rows returned and
  not by queries run. This is a cost model with a price attached, and it is where engineers meet
  input size the hard way: a `SELECT *` over a wide table and a `SELECT one_column` over the same
  table return the same number of rows for wildly different money. If you thought `n` was rows,
  the invoice is the counterexample. Partitioning and column pruning are, in this exact sense,
  techniques for changing what `n` is.

- **Asked as:** *"Given an `n × n` grid, what's the complexity of your flood fill?"* Say `O(n²)`
  and you have to add "where `n` is the side, so linear in the number of cells" or you will spend
  the next while at cross purposes. The interviewer is usually not testing the algorithm here.
  They are testing whether you name your parameter without being asked.

## 5. The mechanism

Choosing `n` is four questions, in order. They take longer to read than to do.

```
   one input, measured three ways

   xs = [1000003, 7, 42, 999999937, 5]

   (a) elements .............. n = 5
   (b) machine words ......... n = 5      <- because every value fits in 64 bits
   (c) bits written down ..... about 100  <- 20 + 3 + 6 + 30 + 3, plus the framing


   ys = [2 ** 4096]

   (a) elements .............. n = 1
   (b) machine words ......... n = 64     <- one value, sixty-four cells
   (c) bits written down ..... 4097

           ^ for xs the three agree up to a constant, so "elements" is safe.
           ^ for ys they do not, and any claim of "one element, so Theta(1)"
             is off by a factor of sixty-four before the procedure starts.
```

*Notice which line changed between the two inputs. Not (a) — the element count is a smaller
number for `ys` than for `xs`, and `ys` is the bigger input. Whenever the element count moves
opposite to the real size, you have found a Thursday.*

**The invariant:** *a cost claim is a function of the parameters you named, and changing which
parameter you name changes what the claim means — not merely its units.* `O(√m)` and `O(2^(b/2))`
describe the very same procedure below.

### A trace

Test whether `999999937` is prime by dividing by every candidate up to its square root, and count
the divisions.

| Quantity | Value |
|---|---:|
| the input, `m` | 999,999,937 |
| elements in the input | 1 |
| bits to write `m` down | 30 |
| divisions actually performed | 31,621 |

One element. Thirty bits. Thirty-one thousand divisions. Whatever the cost of that procedure is a
function of, it is plainly not the element count — and the two candidates left, `m` and `log m`,
disagree with each other so violently that picking between them is the whole exercise: `31621` is
about `√m`, and it is also about `2^15`, which is `2` to the power of half the bit count.

## 6. Line by line

```python
def is_prime(m: int) -> tuple[bool, int]:
    """Return (is m prime, number of trial divisions performed)."""
    if m < 2:
        return False, 0
    divisor, trials = 2, 0
```

The guard first. `0` and `1` are not prime and `m < 2` covers the negatives as well, in one
comparison, without a second branch to get wrong. Returning the trial count alongside the answer
is the habit this whole phase is trying to install: a procedure that reports its own work can be
checked against a derivation, and one that does not has to be believed.

```python
    while divisor * divisor <= m:
        trials += 1
```

`divisor * divisor <= m` and not `divisor <= sqrt(m)`. The two conditions are mathematically
identical and computationally nothing alike: one is an integer multiply and an integer compare —
both exact, both cheap, both defined for every integer Python can hold — and the other converts
an arbitrary-precision integer into a 64-bit floating-point number and hopes. §8 is what
happens when it hopes.

Why stop at the square root at all? Because divisors come in pairs: if `m = a · b` with `a ≤ b`,
then `a ≤ √m`. Finding no divisor at or below `√m` means there is no pair, so there is no divisor.
That is a proof, it is two lines long, and it is the sort of thing you should be able to produce
on demand rather than remember.

```python
        if m % divisor == 0:
            return False, trials
        divisor += 1
    return True, trials
```

The early return is what makes the best case cheap and the worst case a prime. Notice the
asymmetry, the same one 1.2 found: proving *composite* takes one lucky division, and proving
*prime* requires exhausting every candidate. The negative answer is the expensive one again.

**The near-miss.** Here is the version almost everyone writes first:

```python
def is_prime_float(m: int) -> bool:
    divisor = 2
    while divisor <= m ** 0.5:      # <- looks identical to divisor * divisor <= m
        if m % divisor == 0:
            return False
        divisor += 1
    return True
```

It agrees with the correct version on every number you are likely to type by hand, which is what
makes it a near-miss rather than a bug. It fails in two different ways on inputs that are merely
large, and §8 shows both. Both failures come from the same act: converting an integer whose whole
point is that it can be enormous into a float that holds fifty-three bits and no more.

---

## 7. The cost, derived

**Technique: summation.**

The loop runs once per candidate divisor, from `2` upward, while `divisor² ≤ m`. It therefore
runs for every integer in `[2, ⌊√m⌋]`, and each iteration does a constant amount of work — one
multiplication, one comparison, one remainder, one increment. Call that `c`:

```
T(m) = Σ (d = 2 … ⌊√m⌋) c  =  c · (⌊√m⌋ − 1)  =  Θ(√m)
```

Check it: for `m = 999999937` the formula predicts `⌊√m⌋ − 1 = 31622 − 1 = 31621` divisions, and
the instrumented function returns exactly `31621`.

Now restate the same cost in the honest measure. Writing `m` down takes `b = ⌈log₂ m⌉` bits, so
`m = 2^b`, and

```
√m = √(2^b) = 2^(b/2)
```

`Θ(√m)` and `Θ(2^(b/2))` are the same claim about the same procedure. One of them looks like a
square root and the other is exponential in the input size, and this is not a trick of notation —
it is the reason RSA is safe. Nothing changed except which quantity was called `n`.

The measurement, since a claim like that should not be taken on trust. Largest prime below `10^d`,
trial-divided, on CPython 3.12.10 (an Intel Core i3-1115G4):

```
 digits  bits            prime       trials    seconds
      6    20           999983          998      0.000
      8    27         99999989        9,998      0.001
     10    34       9999999967       99,998      0.017
     12    40     999999999989      999,998      0.247
     14    47   99999999999973    9,999,998      1.613
```

Two extra digits multiply the work by exactly ten, forever. Seven extra bits multiply it by ten.
That is the shape of an exponential in the bit count, and it is why the table stops at fourteen
digits: at twenty-four digits the trials column reads a trillion, and no amount of faster hardware
is going to help, because the fix is not a smaller constant, it is a different procedure
(`MTH-05`, Day 184, and the probabilistic tests after it).

| Case | Cost | The input that causes it |
|---|---|---|
| Best | `Θ(1)` — one division | Any even `m`: `1000004` needs a single trial |
| Average | `Θ(√m / log m)`, over `m` drawn uniformly from `[2, M]` | Half of all integers stop at the first division, so the *typical* input is cheap — but a random `m` is prime with probability about `1 / ln M`, and each of those costs the full `√M`. Rare and expensive beats common and cheap: `(1/ln M) · √M` is what the sum comes to. The average is a factor of `log m` below the worst case, which is a discount, not a different shape |
| Worst | `Θ(√m)` = `Θ(2^(b/2))` | `m` prime: `999999937` costs 31,621 |

**Space:** `Θ(1)` auxiliary — two integers, whatever `m` is. Total space is `Θ(b)`, because `m`
itself occupies `b` bits, and for a six-hundred-digit key that is the only term that matters.
Here is the small point most people miss: the *input* is what is large, not the working memory,
and a claim of "constant space" that is silent about a two-thousand-bit input is a claim that has
chosen its `n` conveniently.

**What the constant hides.** `m % divisor` is charged as one operation by 2.1's model, and for
`m` under `2⁶³` that is roughly honest. For `m` with six hundred digits it is not: the remainder
is computed over sixty-four-odd cells and costs proportionally more. So even the `Θ(√m)` above
quietly assumes small `m` — the same assumption, made again, one level down. 2.3 is where that
assumption gets audited.

## 8. When it breaks

The near-miss from §6 breaks loudly on one input and silently on another. Take the loud one first.

```
>>> m = 10**400 + 1
>>> int(m ** 0.5)
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
OverflowError: int too large to convert to float
```

`m ** 0.5` has to make `m` into a float, and the largest float is about `1.8 × 10^308`. A
four-hundred-digit integer is a perfectly ordinary object in Python — it is the size of key
material — and it cannot be turned into a float at all. This is the good failure: it is loud, it
is immediate, and the message names the exact operation that could not be done.

The quiet one is worse. Long before that limit, the conversion stops being exact, because a float
carries fifty-three bits of significand and an integer carries as many as it likes:

```
>>> k = 2**60 + 1
>>> m = k * k
>>> int(m ** 0.5)
1152921504606846976
>>> k
1152921504606846977
>>> m % k == 0
True
```

Read those three numbers together. `m` is a perfect square — it is `k` times `k`, and the last
line says so. The float square root comes back **one short of `k`**. So a loop written as
`while divisor <= m ** 0.5` stops at `1152921504606846976` and never tests `1152921504606846977`,
which is the one divisor at that boundary. The procedure returns `True`. It has declared a
perfect square to be prime, and it does it without a warning, without a traceback, and without
being slow enough to look suspicious.

Notice you cannot catch this one by running it — the loop would need a billion billion
iterations, so the wrong answer arrives long after anybody stopped waiting for the right one. The
only way this bug is ever found is by someone reasoning about the boundary in advance.

**The fix, and why it is not just a patch.** The fix is `divisor * divisor <= m`: integer
arithmetic, exact at every size, no conversion. But the habit worth taking is larger than this
loop. **When the whole point of a value is that it can be arbitrarily large, do not route it
through a type with a fixed number of bits.** Every appearance of `** 0.5`, `float(...)`, `/`
where `//` was meant, or `math.log` inside an integer computation is the same decision being made
again, and each one silently caps your input at fifty-three bits of precision. That is a rule
about `n` and not about square roots, which is why it belongs in this document.

## 9. In production

**At scale.** When `n` gets large enough, the question stops being "what is `n`" and becomes
"which `n` is the one we are paying for", and they are usually not the same one.

A columnar warehouse makes this concrete and unavoidable. In BigQuery a query's price is bytes
scanned; in a row-oriented database the same query's cost is dominated by rows examined. Move a
workload between them without changing a single query and the cost model underneath changes
shape: the optimisation that mattered (fewer rows) is replaced by one that did not exist (fewer
columns, better partition pruning). Teams discover this at the end of a billing cycle.

The same substitution appears whenever data leaves one machine. For a distributed job, the `n`
that decides the wall clock is bytes crossing the network, and a procedure that is linear in
elements can be catastrophic in bytes when the elements are large — the classic being a join key
that is a long string. Counting elements and paying for bytes is the general form of Bhola's
Thursday.

**What a senior reviewer says.**

> "Docstring says `O(n)`. Which `n` — number of files, or total bytes? They differ by six orders
> of magnitude on this bucket and the function does one read per file, so I think you mean files,
> and I think the thing that'll page us is bytes. Name the parameter in the docstring and put the
> other one in the log line."

**What an interviewer probes.** After you state a complexity:

1. *"What is `n` in that sentence?"* — checking whether you can produce the definition on demand.
   Answering "the size of the input" is not an answer; "the number of edges, and `V` separately
   for the vertex loop" is.
2. *"The input is a single integer `m` and your loop runs `m` times. Is that linear?"* — checking
   whether you can tell the value of a number from the size of a number. The answer is that it is
   linear in `m` and exponential in the length of `m`, and that the second is the one that
   decides whether the program finishes.
3. *"Your solution is `O(n · m)` on an `n × m` grid. Is that quadratic or linear?"* — checking
   whether you notice that it is linear in the input (the input *is* `n · m` cells) and that the
   word "quadratic" was doing no work. Naming the parameter dissolves the question.

## 10. Check yourself

Do these the day *after* you read this, with the document closed.

1. A function takes a list of `n` integers and returns their sum. What is `n`, and under what
   assumption is that the right measure?
   <details><summary>answer</summary>

   The number of elements — valid under 2.1's third assumption, that each integer fits in one
   machine word. Drop the assumption (the integers are thousand-digit numbers) and the cost is
   `Θ(n · w)` where `w` is the word count per element, because the additions are no longer unit
   cost. `Θ(n)` was never a claim about addition; it was a claim about addition *on small
   integers*, made without saying so.
   </details>

2. Why is `O(V + E)` written out for graph traversal instead of being collapsed to `O(n)`?
   <details><summary>answer</summary>

   Because `V` and `E` are independent: on `V` vertices, `E` ranges from `0` to about `V²/2`. A
   single `n` would have to be one or the other, and the claim is wrong under either choice for
   half of all graphs. Two parameters is not pedantry here; it is the minimum number that makes
   the sentence true.
   </details>

3. Trial division is `Θ(√m)`. Someone says that is sublinear, so it is fast. Answer them.
   <details><summary>answer</summary>

   Sublinear in the *value*, exponential in the *size*. Writing `m` takes `b ≈ log₂ m` bits, and
   `√m = 2^(b/2)`, so every extra bit of input multiplies the work by about 1.41 and every extra
   digit by about 3.16. The measured table shows the factor of ten per two digits. "Sublinear"
   was true and irrelevant, because it was measured against a quantity nobody has to write down.
   </details>

4. **Break it.** You have a procedure claiming `Θ(n)` for a list of `n` strings. Construct an
   input on which it takes a million times longer than that claim suggests, without changing `n`.
   <details><summary>answer</summary>

   Hold `n` at, say, 1000 and make each string a million characters long. Any procedure that
   compares, hashes, copies or concatenates the elements does work proportional to their length,
   so the true cost is `Θ(n · L)` and the claim silently set `L = 1`. This is the string version
   of the `2 ** 4096` row in the §5 diagram — element count going one way while real size goes
   another. The repair is to name `L`, not to apologise for the constant.
   </details>

5. **Connects to `CPX-01`.** 1.2 said a specification has no complexity. Does a specification have
   an `n`?
   <details><summary>answer</summary>

   It has an input, so it has a size — but no *choice* of `n` has been made, because nothing is
   being counted yet. The size parameter gets chosen at the moment somebody starts costing a
   procedure, and two engineers costing two procedures for the same specification can legitimately
   choose different parameters, which is precisely why their claims cannot be compared until both
   say which one they picked. The specification supplies the input; the analyst supplies the `n`.
   </details>

6. **In review.** A colleague's benchmark doubles the number of *elements* each step and reports
   a ratio near 2, concluding linear. What input would you ask them to add?
   <details><summary>answer</summary>

   One where the elements themselves grow: same element count, larger values or longer strings.
   Their harness varies one parameter and their conclusion is stated as though there were only
   one. It is exactly the Thursday test — hold the head count fixed and put cement on the boat.
   Every `bench.py` in this repo doubles `n` for that reason, and every one of them is blind to
   the second parameter unless you write it in.
   </details>
